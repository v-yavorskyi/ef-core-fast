# Package Review: EfCore.FastExtensions.SqlServer

## Overview
The package extends Entity Framework Core with join-based `ExecuteUpdate` and `ExecuteDelete` helpers. The implementation currently hand-builds SQL statements from LINQ expressions and executes them via `ExecuteSqlRawAsync`.

## Findings
1. **Raw SQL without parameters introduces injection and correctness risks.** Both join helpers build complete SQL strings and run them through `ExecuteSqlRawAsync` without parameters. Value and predicate translation rely on manual string interpolation (for example, `FormatConstant` in both the SET and WHERE translators), so user-provided values flow straight into the SQL. This bypasses EF Core's parameterization, leaves quoting/escaping to bespoke code, and can expose callers to SQL injection or malformed SQL when inputs contain unexpected characters. Consider using EF Core's query pipeline or parameterized `DbCommand` creation rather than string concatenation. ✅ Addressed by adding a shared parameter accumulator that renders placeholders (e.g., `{0}`) and supplies the values to `ExecuteSqlRawAsync`.
2. **Chained `Where` filters are silently dropped.** `ExtractWhereExpression` returns only the first discovered `Where` lambda from the expression chain, so earlier predicates in the pipeline are ignored. As a result, queries like `source.Where(a).Where(b)` will translate only `a` or `b` (depending on ordering), potentially updating/deleting far more rows than the LINQ query represents. The translator needs to aggregate all `Where` calls (and other filtering operators like `Any`) instead of stopping at the first match. ✅ Addressed by collecting every `Where` predicate and combining them with `AND` against a single parameter instance.
3. **Generated SQL is invalid when no predicate exists.** `BuildWhereClause` returns an empty string when it finds no `Where`, but both `ExecuteUpdateJoinAsync` and `ExecuteDeleteJoinAsync` always emit a `WHERE` token. If callers pass a query without filters (or if filters are dropped per finding #2), the resulting SQL ends with `WHERE` and no condition, leading to execution failures. The builders should either omit the `WHERE` clause entirely or enforce that a non-empty predicate exists before running the command. ✅ Addressed by omitting the `WHERE` keyword when no predicate is present.
